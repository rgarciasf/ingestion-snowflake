# Ingestion · Revenue Guard (on Snowflake)

**Which renewals are at risk, and what did we promise them?**

Customer Success teams lose renewals in the gaps between systems. The promise made on a call lives in a transcript, the usage drop lives in the warehouse, and the angry tickets live in the support desk. Today someone reviews accounts by hand every week, and things slip.

Revenue Guard is an agent for a VP of Customer Success. It connects meeting commitments, support tickets and product usage in **Snowflake** and uses **Claude** to:

1. **Find** Enterprise accounts renewing soon with falling usage, urgent tickets and **overdue promises**.
2. **Explain** why, citing the exact SQL result or transcript moment behind every claim.
3. **Verify**: a separate Claude verifier re-derives every number from Snowflake with its own SQL before anything is acted on.
4. **Act**: it proposes risk alerts with owned next steps, and writes them to Snowflake **only after a human approves**.
5. **Govern**: every query runs under the user's Snowflake role, so an EU CSM only ever sees EU accounts (row access policies), with no app-side filtering to trust.

> Inspired by **Ingestion**, our earlier company-brain project (ClickHouse-based). All code, SQL and new data in this repo were written during the Intelligence at Work hackathon (2026-10-23). The fictional "Acme" documents in `data/sources/` (except the new customer call notes) come from that project; the Snowflake data is newly generated by `snowflake/02_seed_pulse.sql`.

## Knowledge graph (shared by both versions)

`ACME.KNOWLEDGE.KG_ENTITIES` / `KG_RELATIONS` hold Ingestion's original graph (`data/graph.json`: teams, people, services, incidents) plus facts added for this project (`data/graph-additions.json`: team leads, key people, CSM-to-account ownership, which incidents hit which customers). That makes 62 entities and 78 relations. The agent's `explore_graph` tool walks it in both directions with a recursive CTE, which links the two versions: *"If Lena Okafor left, which services, incidents and customers would be exposed?"* goes from a person to the Ingest Service, to DI-4410, to Kestrel Bank's renewal. In the Revenue version, customer nodes follow the same region entitlement as customer data.

## Two versions in one app: Revenue and HR

A switch in the sidebar picks the version. Both use the same agent design: investigate, verify, then approve before writing. They also share the same fictional company, Acme.

| | **Revenue** (Revenue Guard) | **HR** (People Guard) |
|---|---|---|
| User | VP Customer Success | HR Business Partner |
| Question | Which renewals are at risk, and what did we promise them? | Which teams are at risk of losing people, and what did we promise them? |
| Promises from | Customer calls (`data/sources/meetings/`) | 1:1s, retros, staffing reviews (`data/sources/people/`) |
| Signals | Usage trend, urgent tickets, CSAT, days to renewal | After-hours work, pages, PTO taken, eNPS / intent-to-stay, voluntary exits |
| Snowflake data | `ACME.PULSE` + `ACCOUNT_HEALTH` + semantic view `PULSE_ANALYTICS` | `ACME.PEOPLE` + `TEAM_HEALTH` + semantic view `PEOPLE_ANALYTICS` |
| Write-back | `ACME.BRAIN.RISK_ALERTS` | `ACME.BRAIN.PEOPLE_ACTIONS` (pay-affecting steps routed to Total Rewards) |
| Personas | `ACME_CS_LEAD`, `ACME_CSM_EU` | `ACME_HRBP`, `ACME_MGR_DATA_INFRA` |
| Governance | Row access by customer region | Row access by team, **salary masking**, **aggregation policy** (survey groups ≥ 5), HR notes for HRBPs only |

The two versions are linked: the incidents that put customers at risk in the Revenue version (DI-4410, Android 4.2, INC-2291) are the same ones burning out Data Infra, Product Eng (mobile) and Payments in the HR version.

**HR performance data (reviews, competency ratings, goals, peer feedback).** It is synthetic, for the same fictional employees. Its shape follows a profile of **aggregate statistics** (rating distributions, the self vs manager gap, completion rates, goal shape, feedback rate) computed read-only inside a real HR system by `scripts/profile-ascend.ts`. Groups under 5 were suppressed, and no names, IDs, titles or text were read. Competency labels were replaced with generic names. The profile itself (`data/hr-profile.json`) is git-ignored and never published; only the generated synthetic SQL (`snowflake/hr/11_hr_performance.sql`) is in the repo.

**HR guardrails.** Analysis is team-level by default. There are no individual "flight risk" scores, and the signals are never used for performance or disciplinary decisions. Individuals are named only when they appear in a promise (for example a promotion case). Survey data is anonymous and is enforced by Snowflake to groups of 5 or more.

## Architecture

```
                    ┌──────────────── Claude Opus 5.5: investigator (Claude API) ─────────────────┐
 question + role ─▶ │ run_sql · search_knowledge · get_commitments · verify_numbers · propose_alerts │ ─▶ cited answer
                    └──────┬──────────────────┬────────────────────┬──────────────────┬────────────┘
                           │                  │                    │                  │ approval card (human)
            Semantic view + tables     Cortex Search         Claude Sonnet 5.5     INSERT RISK_ALERTS
            (PULSE_ANALYTICS,          (KNOWLEDGE_SEARCH     verifier: own SQL     + AGENT_TRACES
             ACCOUNT_HEALTH)            over docs+meetings)   per claim
                           └──────────── all under the persona's Snowflake ROLE ─────────────┘
                                         row access policies by data-residency region

 Offline, in Snowflake: AI_COMPLETE(claude-…) reads every customer call → ACME.BRAIN.COMMITMENTS
                        (owner, due date, quote, status from follow-up notes, citation chunk)
```

| Layer | Snowflake | Claude |
|---|---|---|
| Surface | Snowflake account, roles per persona | Web app (Node), agent loop on the Claude API |
| Context | Semantic view `PULSE_ANALYTICS` (metric definitions), `ACCOUNT_HEALTH` view, Cortex Search over docs and transcripts | System prompt and schema guide |
| Intelligence | `AI_COMPLETE` with Claude in Cortex (commitment extraction) | Opus 5.5 investigates, Sonnet 5.5 verifies |
| Action | Governed write-back to `ACME.BRAIN.RISK_ALERTS`; traces in `AGENT_TRACES` | Human-in-the-loop approval card |
| Trust | Row access policies (`ACCOUNT_REGION_POLICY`, `DOC_ACCESS_POLICY`), read-only SQL guard | Every number cited to a query; independent verification |

## Data (all synthetic, no PII)

- `ACME.PULSE`: 6,000 workspaces, ~10M product events, invoices and ~29K support tickets (Apr to Oct 2026), with built-in stories: the Android 4.2 crash spike, the INC-2291 billing incident, the DI-4410 EU ingestion delays and the Reports v1 deprecation.
- Eight named Enterprise "story" accounts (Kestrel Bank, Cobalt Logistics, Nord Games, Atlas Retail, Brightline Health, Harbor Fintech, Lumio Learning, Fern Media) whose usage, tickets and renewal dates match their call transcripts in `data/sources/meetings/`.
- `ACME.KNOWLEDGE`: 33 documents, 153 search chunks (policies, product docs, tickets, meeting transcripts).

## Setup

```bash
npm install
cp .env.example .env          # Snowflake account/user/password (or PAT) and ANTHROPIC_API_KEY
npm run knowledge             # regenerates snowflake/03_knowledge.sql from data/sources
npm run hr:data               # regenerates snowflake/hr/10_hr_seed.sql + 11_hr_performance.sql (needs data/hr-profile.json)
npm run graph                 # regenerates snowflake/07_knowledge_graph.sql from data/graph*.json
npm run setup                 # runs snowflake/01..06 (Revenue) then snowflake/hr/10..14 (HR) as ACCOUNTADMIN
npm start                     # http://localhost:3000
```

`06_commitments_claude.sql` and `hr/14_hr_commitments_claude.sql` use a Claude model through Cortex `AI_COMPLETE`. Set `CLAUDE_MODEL` at the top of each file to a Claude model available in your Snowflake region.

## Demo script (3 minutes)

1. **Hook:** "Kestrel Bank renews in 39 days. Promises we made them are overdue, and their usage just dropped about 40%. Nobody on the team has connected those dots."
2. As **VP Customer Success**, click the first example question. Watch the trace: semantic-view SQL, Cortex Search over transcripts, commitments, then the **Sonnet verifier** re-checking each number.
3. Click an orange **[q3]** chip to see the exact SQL and rows; click a blue **doc** chip to see the transcript moment.
4. **Approve** the alerts, then open **Risk alerts**: they are now rows in Snowflake.
5. Switch to **EU CSM** and ask the same question: only eu-central accounts come back. That filtering is done by Snowflake, not by the app.

## HR demo script (3 minutes)

1. **Hook:** "Data Infra has been paged every night since DI-4410. They've stopped taking time off, two people have already quit, and the promises their manager made them are overdue."
2. Switch to **HR** as the **HR Business Partner** and run the first example. The trace shows `TEAM_HEALTH`, the HR notes found by Cortex Search, promises to employees, then the Sonnet verifier.
3. Open a **doc** chip to see the exact line in the 1:1 or retro where the promise was made.
4. **Approve** the retention plans. Pay-affecting steps are flagged "needs Total Rewards", the same rule as the off-cycle approvals in the Compensation Bands policy.
5. Switch to **Data Infra Manager**: only their own team is visible, salaries are masked and HR 1:1 notes are hidden. All of this is enforced by Snowflake.
