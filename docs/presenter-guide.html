1. The system in 30 seconds

Say: “SignalHR is an HR agent built on Snowflake and Claude. It tells an HR Business Partner which teams are about to burn out or lose people, and which promises we made them that we haven't kept. It also approves time off without breaking on-call coverage, and prepares performance calibration. Every number is checked by a second model, nothing is saved until a human approves, and Snowflake decides who can see what.”

If you remember only one line: “Snowflake governs. Claude reasons and verifies. People decide.”

2. How it works, in plain words

Think of it as four layers, from the data at the bottom to the person at the top.

1
The data lives in Snowflake (the “single source of truth”).
A fictional company, Acme, with 187 employees in 14 teams. For each person we have workload per week (after-hours hours, pager alerts, days off), anonymous pulse surveys, performance reviews and goals, time-off requests, and the on-call schedule. We also loaded HR notes (1:1s, team retros, staffing reviews) and policies (PTO, on-call recovery).
Ready-made summaries do the maths: TEAM_HEALTH (one row per team with all risk signals), TIME_OFF_REVIEW (one row per request with the policy checks) and PERFORMANCE_SUMMARY (rating mix per team).
2
Snowflake enforces the privacy rules, not our app.
Each user type is a Snowflake role. The HR Business Partner sees all teams. The Data Infra Manager sees only their own team, salaries are hidden from them, and sick or parental leave shows as “leave”. Anyone can read survey answers only in groups of 5 or more. HR notes are visible to HR only.
Even if the AI tried, the database would not return what the role may not see.
3
Claude does the thinking, in three roles.
Claude Opus 5.5 is the investigator. It decides which questions to ask the data, runs the SQL, searches the HR notes, and writes the answer with citations.
Claude Sonnet 5.5 is the verifier. Before anything is proposed, it re-calculates every key number with its own SQL and says pass or fail.
Claude inside Snowflake (Cortex AI_COMPLETE) is the reader. Ahead of time it read every HR note and pulled out each promise a manager made (who, to whom, by when, the exact quote), plus whether a later note says it was done, late or broken.
4
A human approves every action.
The agent proposes retention plans or time-off decisions on an approval card. Nothing is written to Snowflake until someone clicks Approve. Anything that touches pay is routed to Total Rewards and never executed by the agent. Every run is logged (AGENT_TRACES) for audit.

Lifecycle of one request

  1. The browser posts the question and persona to /api/ask.
  2. The server opens (or reuses) the Snowflake connection for that role with secondary roles off, so only that role's grants and policies apply.
  3. Opus gets the system prompt (mission, schema guide, privacy rules) and loops: think → call a tool → read the result, typically 10–20 times. Each step streams to the trace.
  4. Before proposing, Opus calls verify_numbers. Sonnet checks independently; anything that fails is corrected or removed.
  5. A proposal tool pauses the loop and shows an approval card. On Approve, the server inserts the rows into ACME.BRAIN using the same role.
  6. Opus writes the final answer with q (SQL) and doc (note) citations. The whole run (steps, tokens, verdicts) is saved to AGENT_TRACES.

How the data was built

  • All SQL is in the repo: snowflake/hr/10_… to 17_… (seed, performance, views, governance, Cortex extraction, time off, performance views).
  • Synthetic people generated with Snowflake GENERATOR and a seeded script (scripts/build-hr-sql.mjs); 2 story teams (Data Infra, Product Eng) designed to show the signals.
  • Performance shape from aggregate-only statistics of a real HR system (groups < 5 suppressed); the profile file is git-ignored and never loaded into Snowflake.

Tech stack in one line

Snowflake (tables, views, semantic views, Cortex Search, Cortex AI_COMPLETE, governance policies) · Claude Opus 5.5 + Sonnet 5.5 via @anthropic-ai/sdk · Node 24 + TypeScript, no framework · single-file HTML UI · repo: github.com/rgarciasf/ingestion-snowflake

3. Words you may need to explain

TermIn one sentence
Semantic viewA Snowflake object that stores the official definitions of metrics (for example “headcount” or “after-hours per person per week”), so every query uses the same meaning.
Cortex SearchSnowflake's built-in search over text (here the HR notes and policies). It combines keyword and meaning-based search.
Cortex AI_COMPLETECalling Claude from inside a Snowflake SQL query. We use it to turn notes into a structured table of promises.
Row access policyA Snowflake rule that filters which rows a role can see (the manager sees only Data Infra).
Masking policyA rule that hides a column's value for some roles (salary shows as empty for the manager).
Aggregation policyA rule that only allows totals and averages over groups of at least 5 (anonymous surveys).
Knowledge graphA map of who owns which service and which incident hit which customer. It answers “if Lena left, what breaks?”
VerifierThe second Claude that re-derives the numbers before anything is proposed.
Approval card / write-backThe human-in-the-loop step. Approved items are saved to ACME.BRAIN tables.
Agent traceThe step-by-step log of what the agent did, shown live and saved in Snowflake.
Synthetic dataEvery person is fictional. The shape of the performance data (rating mix, completion rates) comes from aggregate-only statistics of a real HR system, groups under 5 suppressed, never published.
PersonaWho you are acting as. Each persona is a real Snowflake role, switched in the left sidebar.

4. The 3-minute pitch script

The organisers' rule: open strong (≤ 30 s: who has the problem and why it matters), spend most of the time on a live demo, land the impact. Then 2 minutes of Q&A.

Timing trick: a full agent run takes 1.5–2.5 minutes. Click the time-off question right after the hook and talk over it while it runs. It will finish during your architecture explanation. The salary question answers in about 5 seconds, so it's a safe live moment.

0:00–0:30 Hook

DoStart on the Overview as HR Business Partner. Point at the Data Infra card.
Say“HR usually finds out a team is burning out when someone resigns. The signals were there: pager alerts, after-hours work, time off not taken, a falling pulse score. So were the promises managers made in 1:1s, but nobody tracked them. At our demo company, Data Infra's engagement went from +15 to −85 in a month, two engineers quit, and four promises to that team are overdue.”

0:30–1:20 Live demo part 1: the manager's time-off review (runs while you talk)

DoClick the persona Data Infra Manager → Ask the agent → the example “Review the pending time-off requests…”.
Say(while the trace runs) “I'm now the Data Infra manager. SignalHR is reading Snowflake under my role: the requests, the on-call schedule, team coverage and the comp days we owe. Each step appears in this trace. Claude Opus is doing the investigation, and the cyan steps are a second Claude, Sonnet, re-checking every number before anything is proposed. Under the hood it's all Snowflake: semantic views for the definitions, Cortex Search over the 1:1 notes, and Claude inside Cortex already extracted every promise from those notes.”

1:20–1:50 Governance moment (do this in a second browser tab if the time-off run is still going)

DoSecond tab, same persona: type “What is Lena Okafor's salary, and what did she say in her 1:1?” and press Ask (about 5 s).
Say“Now watch what happens if I ask for something I shouldn't see. Refused, and not by a prompt: Snowflake itself masks salaries for this role and hides HR notes. The same question as the HR Business Partner would get an answer. That's row access, masking and aggregation policies doing the work.”

1:50–2:30 Live demo part 2: the result and approval

DoBack to the first tab. Show the decisions table (approve with swap, and so on), click Approve & write, then click one orange q chip to show the SQL.
Say“Nine requests reviewed. Four clashed with someone's own on-call week, so it proposes named swaps instead of declining, and it schedules the comp days we owe before they expire. Nothing is saved until I approve, and when I do, it's written back to Snowflake and logged. Every number links to the exact query that produced it.”

2:30–3:00 Impact and what's next

Say“Instead of finding out at the exit interview, HR gets a verified answer in a couple of minutes, with owners and dates, written back to Snowflake. The same agent also prepares performance calibration at team level, never rating individuals. It runs inside the company's own Snowflake under their existing roles, so it's deployable on day one. Next: connect the HRIS and send every HRBP a weekly digest. Snowflake governs, Claude reasons and verifies, people decide.”

6. Demo runbook and fallbacks

Before you walk up (5 minutes earlier)
  • The app runs at http://localhost:3100. If not: in the project folder run PORT=3100 node --env-file=.env src/server.ts.
  • Demo data is clean. If you already approved things, ask Claude to “reset the demo data” (otherwise the approval cards won't appear).
  • Open two tabs; both start on Overview as HR Business Partner.
  • Browser zoom 90–100%; close other tabs; turn on Do Not Disturb; laptop on power.
  • Have the video ready: docs/people-guard-demo.mp4. It was recorded under the earlier name “People Guard”; if asked, say “that was our working title”.
If something goes wrong
  • A run is slow: keep talking (use the architecture lines from section 2). Approval cards wait up to 5 minutes.
  • “Usage limit” error: the Anthropic key hit its spend limit. Switch to the video and say so honestly.
  • No approval card (“already decided”): the data wasn't reset. Show the answer and the Retention plans page instead.
  • Wi-Fi or Snowflake down: play the video, then walk through the architecture page.
  • Red SQL error in the trace: that's normal. The agent fixes its own query; say “it self-corrects”.
Safe, fast moments you can always show live
  • Overview page: KPI cards and team risk cards (instant).
  • Teams page: the table view, then switch persona to show that the manager sees 1 team and salary is hidden (about 5 s).
  • Salary question as the manager: refused in about 5 s.
  • Retention plans page: what has been approved and written.

7. Q&A: likely questions and short answers

Isn't this employee surveillance?

No. It works at team level and makes no individual flight-risk scores. Surveys are anonymous and only readable in groups of 5+. Its signals are never used for performance or discipline. Its job is to make managers keep their promises and protect rest time.

How do you stop the AI from making up numbers?

Every number comes from a SQL query against Snowflake, a second model re-derives it independently, and the UI links each number to the exact query and rows. In one run the verifier rejected 2 of 14 numbers before HR saw them.

Is any of this real data?

No. Every person and note is fictional. To make the performance patterns realistic, we computed aggregate-only statistics from a real HR system (groups under 5 suppressed, no names, IDs or text) and generated synthetic people from that shape. The profile was never loaded into Snowflake or published.

Why Snowflake and Claude together, and not just a chatbot?

Snowflake gives governed context: the same roles and policies the company already trusts, enforced at the data layer. Claude gives multi-step reasoning, verification and extraction, including inside Snowflake with Cortex AI_COMPLETE. A chatbot over a document dump has neither the governance nor the verified numbers.

What does the AI decide on its own?

Nothing that changes data. It investigates and proposes; a human approves every write; pay-affecting steps go to Total Rewards and are never executed by the agent.

Why two different models?

Matching model to task, as the kickoff talk recommended. Opus for open-ended investigation, Sonnet for the bounded verification job, and Claude in Cortex for extraction. The verifier being independent is the point: it checks the investigator.

How did you get the promises out of the notes?

Claude inside Snowflake (Cortex AI_COMPLETE with a JSON schema) read each 1:1, retro and staffing note and extracted every promise with owner, recipient, category, due date and the exact quote. It then read the People Team follow-up notes to mark each one done, open or broken.

How long does it take, and what does it cost?

One to two and a half minutes per full investigation, about 80K–190K tokens, so well under $1 with Claude Opus 5.5. Compare that with hours of HRBP and manager time per review.

How would a company deploy it?

Inside their own Snowflake account: map personas to existing roles, point the views at their HRIS tables (Workday, Ascend), load meeting notes, done. No data leaves their governance boundary.

What about the manager seeing their team's reviews?

Managers see only their own team (row access policy); survey data only in groups of 5+; HR notes are HR-only. Performance analysis is aggregated by team; the agent never ranks individuals.

What would you build next?

An HRIS connector (aggregate-first, same policies), meeting-notes ingestion (Granola, Zoom, Teams), a weekly “teams at risk” digest per HRBP, and a formal eval set.

What was hardest?

Making governance real. Our first test showed a manager seeing every salary, because the hackathon user had every role active at once. We now run each persona with secondary roles off, and we protected search chunks too. The aggregation policy even blocked our own view, so we pre-aggregate survey scores with the 5+ rule built in.

Did you build all of this today?

Yes. The idea comes from our earlier project, Ingestion (a company-brain agent on ClickHouse), but all code, SQL and data in this repo were written today. There's also a Revenue version we built and put on hold to focus.

9. Be honest about

  • Synthetic data. The story teams were designed. Say “fictional company, realistic shape” and don't claim real-world results.
  • Speed. Full runs take 1.5–2.5 minutes. They're agentic and verified, not instant chat.
  • Search filtering. Cortex Search runs with the owner's rights, so search results are filtered per persona in the app; direct table reads are blocked by Snowflake policies.
  • No formal eval suite yet. We have the runtime verifier and known-answer checks; a scored eval set is next.
  • Revenue version on hold. It exists in the repo (renewals and AI token usage), but we focused the submission on HR.
