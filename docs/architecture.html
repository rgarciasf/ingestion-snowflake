Ingestion · Revenue Guard: system architecture

An agent for a VP of Customer Success that answers “Which renewals are at risk, and what did we promise them?”. It connects meeting commitments, support tickets and product usage in Snowflake, uses Claude to investigate and verify, and writes risk alerts back only after a human approves.

Track: Internal Two versions: Revenue · HR Snowflake = governed source of truth Claude = investigate · verify · act All data synthetic, no PII

System architecture

Three parts: the people (personas), a small Node web app that runs the agent loop, and the Snowflake account that holds data, search, governance and write-back.

Data flow: one question, end to end

Example: “Which Enterprise accounts renewing in the next 60 days are at risk, and what did we promise them?”

  1. Ask as a personaThe user picks a persona (Snowflake role) and asks. The browser POSTs to /api/ask and receives a live stream of events (NDJSON): steps, approval cards, the answer.
    Web app
  2. PlanClaude Opus 5.5 gets the question, the persona and a schema guide (semantic view, health view, commitments). It decides which tools to call, often several in parallel.
    Claude
  3. Find the “how much”run_sql queries ACCOUNT_HEALTH and the PULSE_ANALYTICS semantic view: ARR, days to renewal, usage change, urgent tickets, CSAT. A guard allows only one read-only statement; each result gets a citation id (q1, q2…).
    Snowflake
  4. Find the “why”get_commitments lists overdue promises extracted earlier by Claude in Cortex. search_knowledge runs Cortex Search over transcripts and tickets. Results about accounts outside the role's region are withheld, based on what Snowflake lets that role see.
    Snowflake
  5. Verifyverify_numbers hands the key figures to a separate Claude Sonnet 5.5 agent. It writes its own SQL, re-derives each number and returns pass / fail. Failed numbers must be fixed before any alert is proposed.
    Claude
  6. Propose and approvepropose_risk_alerts shows an approval card: risk level, ARR, renewal date, summary and owned next steps. The agent waits for a human to click Approve or Decline.
    Human
  7. Write backOn approval, alerts are inserted into ACME.BRAIN.RISK_ALERTS under the same role, with the approver recorded. Nothing is written on decline or after a 5-minute timeout.
    Snowflake
  8. Answer and auditThe cited answer is streamed to the UI, where orange chips open the SQL and rows and blue chips open the transcript. The full run (steps, tokens, latency) is saved to ACME.BRAIN.AGENT_TRACES.
    Web app

HR guardrails

Team-level by default. No individual “flight risk” scores. Never used for performance or disciplinary decisions. Individuals named only when they appear in a promise.

Trust and governance

Enforced by Snowflake

  • One connection per persona role. The app never filters customer data itself.
  • ACCOUNT_REGION_POLICY on workspaces, events, invoices, tickets, commitments and alerts.
  • DOC_ACCESS_POLICY hides manager-only documents from non-leads.
  • The same question as the EU CSM returns only eu-central accounts.

Enforced by the agent design

  • Read-only SQL guard: one statement, SELECT / WITH / SHOW / DESCRIBE only.
  • Every number cites a query; every document claim cites a chunk.
  • Independent verifier before any action.
  • Writes only through the approval gate; every run is saved as a trace.
